# Affiliate Revenue Share (REVSHARE)

**Status:** Design approved 2026-04-20
**Scope:** THORChain protocol change — `x/thorchain` module and related keeper state.

## Problem

THORChain's existing affiliate system takes a cut of the **user's input amount** at swap time (via memo `affiliate` / `affiliate_bps`). There is no mechanism to share the **protocol's own income** (liquidity fees collected on swaps) with the affiliate that drove the swap. This limits the business models affiliates can build on top of THORChain — they cannot earn a residual share of the protocol revenue they generate without taxing their users more heavily.

## Goal

Let the protocol assign each affiliate THORName a configurable share (in basis points) of the RUNE liquidity fees generated by swaps that named them as the first affiliate. The share is paid out of protocol income, **not** out of the user's swap.

- Per-THORName dial: operational mimir `REVSHARE-<thorname>` in bips.
- Hard cap: 5000 bps (50%) per thorname, enforced at mimir-set time.
- Exactly one affiliate per swap is eligible: the first one listed in the memo (strict, no fall-through).
- Fees roll up across each sub-swap of a streaming swap.
- Paid into the existing `AffiliateCollector` so preferred-asset conversion continues to work.
- Deducted off the top of end-of-block system income, before any other split.

## Non-Goals

- Not a change to the user-side `affiliate_bps` cut; that path is untouched.
- Not applied to LP add/withdraw fees, savers, trade accounts, secured asset mint/burn, rune pool, or block emissions. Only swap liquidity fees (including streaming sub-swaps) are in scope.
- Not a governance change: operational mimir controls this dial, same governance surface as other operational keys.
- No state migration (accumulator starts empty each block).

## Architecture

```text
┌─────────────────────────┐
│  Swap handler (incl.    │   1. Each time a liquidity fee is recorded,
│  streaming sub-swap)    │      if the swap's first memo affiliate
└───────────┬─────────────┘      resolves to an active THORName, call
            │                    AddAffiliateLiquidityFee(thorname, fee).
            ▼
┌─────────────────────────┐
│ New keeper keyspace:    │   2. Per-block accumulator keyed by
│ AffiliateLiquidityFees  │      thorname. Cleared at end of block.
└───────────┬─────────────┘
            │
            ▼
┌─────────────────────────┐
│ UpdateNetwork()         │   3. systemIncome = blockReward +
│  end-of-block           │      totalLiquidityFees.
│                         │      For each (thorname, accrued):
│                         │        bps = mimir("REVSHARE-"+thorname)
│                         │        payout = accrued * bps / 10_000
│                         │        Reserve → AffiliateCollector[owner]
│                         │        systemIncome -= payout
│                         │        emit rev_share event
│                         │      Clear accumulator.
│                         │      Continue dev-fund / burn / TCY /
│                         │      marketing / POL / pendulum with
│                         │      reduced systemIncome.
└─────────────────────────┘
```

**Bookkeeping invariant.** At end-of-block, the reserve has just received `totalLiquidityFees` as part of system income roll-up. Rev-share is paid from the reserve to `AffiliateCollector`. No RUNE is minted; `systemIncome` is reduced by exactly the sum of payouts before downstream splits run.

**Per-affiliate arithmetic.** A thorname's payout is `REVSHARE_bps × their_attributed_liquidity_fees`, never `REVSHARE_bps × total_system_income`. "Off the top" describes only the ordering — `systemIncome_new = systemIncome − Σ payouts`.

## Components

### 1. New keeper state: `AffiliateLiquidityFees`

- Keyspace: `AffiliateLiquidityFee/<thorname>` → `sdk.Uint` (RUNE, 1e8).
- Lifecycle: entries exist only within a single block. Written during swap fee recording; deleted at end of block after payout.
- Kept separate from `AffiliateCollector` (which stores paid-out, cross-block balances awaiting preferred-asset conversion). Different lifecycle, different unit of account.

Public methods on the keeper (expected file: `x/thorchain/keeper/v1/keeper_affiliate_liquidity_fee.go`, interface addition + `AffiliateLiquidityFee` struct in `x/thorchain/keeper/keeper.go`):

```go
type AffiliateLiquidityFee struct {
    Thorname string
    Fee      cosmos.Uint
}

AddAffiliateLiquidityFee(ctx cosmos.Context, thorname string, fee cosmos.Uint) error
GetAffiliateLiquidityFees(ctx cosmos.Context) ([]AffiliateLiquidityFee, error)
DeleteAffiliateLiquidityFees(ctx cosmos.Context)
```

`GetAffiliateLiquidityFees` returns a slice of entries sorted lexicographically by upper-cased `Thorname` (the IAVL store iteration order, preserved explicitly so the contract is in the return type rather than relying on iterator semantics). **The slice ordering is consensus-critical** — the end-of-block deduction loop iterates the slice and emits events in slice order, so a non-deterministic ordering across nodes would diverge state. Returning a slice (rather than a `map[string]cosmos.Uint`) makes the determinism guarantee a property of the type and prevents callers from accidentally introducing `for ... range map` iteration.

### 2. Swap-path attribution hook

Called at the same site where liquidity fees are already recorded (today this flows into `AddToLiquidityFees`). A parallel attribution call runs once per liquidity fee recording:

```go
func attributeAffiliateLiquidityFee(ctx cosmos.Context, mgr Manager, swap SwapCtx, liquidityFeeRune cosmos.Uint) {
    if liquidityFeeRune.IsZero() { return }
    if len(swap.Affiliates) == 0 { return }

    firstAffiliate := swap.Affiliates[0]       // strict first, no fall-through
    thorname, ok := resolveActiveThorname(ctx, mgr, firstAffiliate)
    if !ok { return }                          // raw address / expired / missing

    _ = mgr.Keeper().AddAffiliateLiquidityFee(ctx, thorname.Name, liquidityFeeRune)
}
```

`resolveActiveThorname` rules:

- The affiliate string must match an existing `THORName`.
- `ExpireBlockHeight > ctx.BlockHeight()`.
- The REVSHARE mimir is **not** checked here. Accumulation happens regardless; the mimir lookup runs at payout time. This keeps attribution resilient to operators enabling/disabling mid-block.

**Streaming swap propagation.** The parent swap's memo affiliate must be available at each sub-swap's fee-recording site. The implementation must verify the streaming swap manager already propagates the affiliate on the in-flight swap record, and if it does not, carry the field through. (Flagged as an implementation-time verification step; no change to the design.)

**No change to `skimAffiliateFees`.** The user-side cut is independent; REVSHARE is additive and comes out of protocol income.

### 3. End-of-block deduction in `UpdateNetwork`

Location: `x/thorchain/manager_network_current.go`, inserted right after `systemIncome = blockReward + totalLiquidityFees` and **before** any other split.

```go
systemIncome := blockReward.Add(totalLiquidityFees)

entries, err := keeper.GetAffiliateLiquidityFees(ctx)
if err != nil {
    // Skip-and-continue: an iteration failure must not stop downstream
    // splits or leave the accumulator un-cleared.
    ctx.Logger().Error("fail to read affiliate liquidity fees", "error", err)
    entries = nil
}
totalRevShare := cosmos.ZeroUint()

// entries is sorted lex by Thorname; iterating in slice order is
// deterministic across nodes.
for _, entry := range entries {
    thornameName := entry.Thorname
    accrued := entry.Fee

    var ownerForEvent cosmos.AccAddress
    thorname, err := keeper.GetTHORName(ctx, thornameName)
    if err == nil {
        ownerForEvent = thorname.Owner
    }
    // Note: a missing thorname does NOT skip the event. The rev_share
    // event is the canonical record of gross attribution; emitting it
    // with empty owner and payout=0 keeps indexers consistent.

    bps, _ := keeper.GetMimirWithRef(ctx, constants.MimirTemplateRevShareThorName, thornameName)
    payout := cosmos.ZeroUint()

    if err == nil && bps > 0 {
        payout = common.GetSafeShare(
            cosmos.NewUint(uint64(bps)),
            cosmos.NewUint(10_000),
            accrued,
        )
        if !payout.IsZero() {
            collector, _ := keeper.GetAffiliateCollector(ctx, thorname.Owner)
            collector.RuneAmount = collector.RuneAmount.Add(payout)
            keeper.SetAffiliateCollector(ctx, collector)

            if err := keeper.SendFromModuleToModule(ctx, ReserveName, AffiliateCollectorName,
                common.NewCoins(common.NewCoin(common.RuneAsset(), payout))); err != nil {
                ctx.Logger().Error("revshare transfer failed", "thorname", thornameName, "err", err)
                // Roll back the collector change so state stays consistent
                // when the bank transfer fails.
                collector.RuneAmount = common.SafeSub(collector.RuneAmount, payout)
                keeper.SetAffiliateCollector(ctx, collector)
                payout = cosmos.ZeroUint()
            } else {
                totalRevShare = totalRevShare.Add(payout)
            }
        }
    }

    // Always emit the event for every accumulator entry, regardless of
    // whether REVSHARE is set or the thorname still exists. NewEventRevShare
    // clamps a -1 ("unset") bps sentinel from GetMimirWithRef to 0.
    eventMgr.EmitEvent(ctx, NewEventRevShare(thornameName, ownerForEvent, accrued, bps, payout))
}

keeper.DeleteAffiliateLiquidityFees(ctx)
systemIncome = common.SafeSub(systemIncome, totalRevShare)

// existing splits run unchanged off the reduced systemIncome:
// dev fund, burn, TCY stake, marketing fund, POL reserve, bond/LP pendulum
```

**Safety properties.**

- `systemIncome` cannot go negative: set-time validation caps each mimir at 5000 bps, so per-entry payout is bounded by `5000/10000 × accrued`, and `Σ accrued ≤ totalLiquidityFees` by construction.
- A reserve transfer failure logs and skips; the accumulator is still cleared so the failure does not carry into the next block.
- If the thorname disappears between fee attribution and payout (`GetTHORName` miss), the payout is skipped and the RUNE remains in the reserve.

### 4. Mimir: validation and operational classification

**Template constant** in `constants/mimir_strings.go`:

```go
const MimirTemplateRevShareThorName = "REVSHARE-%s"
```

**Hard cap constant** in `constants/constants.go` (or the appropriate versioned constants file): `RevShareMaxBps = 5000`.

**Validation at mimir-set time.** In the mimir handler (and in node-mimir vote validation), reject `REVSHARE-<X>` unless:

- `<X>` is an existing thorname.
- `0 ≤ value ≤ RevShareMaxBps`.

```go
if strings.HasPrefix(key, "REVSHARE-") {
    thornameName := strings.TrimPrefix(key, "REVSHARE-")
    if !keeper.THORNameExists(ctx, thornameName) {
        return errors.New("REVSHARE mimir requires existing thorname")
    }
    if value < 0 || value > RevShareMaxBps {
        return errors.New("REVSHARE value must be between 0 and 5000 bps")
    }
}
```

**Operational classification.** Add `"REVSHARE"` to the `partialMatches` list in `keeper_mimir.go`'s `IsOperationalMimir()`. This ensures:

- Clearable via operational vote (low quorum).
- Purged from node-mimir votes at end-of-block after they take effect (`PurgeOperationalNodeMimirs`), matching the HALT / PAUSE pattern.

**Semantics.**

- Value = 0 → no payout (distinct from "not set" but functionally equivalent).
- Unset (entry deleted) → no payout next block onward.

**THORName character-set limitation.** `IsValidTHORName` accepts `[a-zA-Z0-9+_-]`, but `MimirKeyRegex` (which gates every mimir-set call) accepts only `[a-zA-Z0-9-]`. A thorname containing `_` or `+` registers fine, but `REVSHARE-<thorname>` for it will be rejected at mimir-set time by the generic key-format check (`mimirValidKey`) before the REVSHARE-specific validation above runs. Operators who want REVSHARE eligibility must register a thorname using only letters, digits, and `-`.

### 5. Event emission

New event type `rev_share`, emitted at end-of-block **for every thorname with a non-zero accumulator entry**, regardless of whether REVSHARE is set. This gives downstream indexers a single source of truth for both gross attribution and net payouts.

```text
type: rev_share
attributes:
  thorname:        <name>
  owner:           <thor1... owner address>
  accrued_fee:     <RUNE liquidity fee attributed this block, 1e8>
  bps:             <REVSHARE mimir value applied; 0 if unset>
  payout:          <RUNE moved reserve -> affiliate collector, 1e8; 0 if no payout>
```

Semantics:

- **Every** entry in the per-block accumulator produces one event, even when `bps == 0` and `payout == 0`. The `accrued_fee` field is the gross liquidity fee attributed to that thorname this block and is always present.
- When REVSHARE is set, the same event also carries the payout details.

Follows the existing `EventX` pattern in `x/thorchain/types/event.go`, Protobuf-registered for indexers.

**Implementation note:** the end-of-block loop iterates the accumulator once; for entries where REVSHARE is not set or is zero, it skips the reserve transfer but still emits the event.

## Version Gating

Both the `UpdateNetwork` deduction and the swap-handler attribution are gated behind a version bump (e.g., `V3_X_0`) via the usual `GetVersion` switch in `manager_network_current.go` and the swap handler. Mimir validation is additive and safe to deploy immediately.

No state migration needed — the accumulator starts empty each block.

## Risks and Mitigations

- **Misconfiguration.** Operational mimir is the dial. Set-time validation enforces the 5000-bps hard cap, bounding the downside of any single REVSHARE entry.
- **Thorname squatting.** Someone registers a thorname hoping to collect. The REVSHARE mimir is the gate — no mimir, no payout. Operational governance controls the mimir.
- **Indexer lag.** The `rev_share` event is emitted every block; indexers can account without state reads.
- **Streaming-swap plumbing gap.** If the parent swap's first affiliate is not already available at sub-swap fee recording, the implementation must add a field to the in-flight swap record. Verify during implementation.

## Downstream Consumers

Midgard (and any other event indexer) is expected to index the `rev_share` event and expose windowed queries per thorname (e.g., rolling 24h or 30d gross attributed liquidity fees, or rolling rev-share earnings). This sits outside the thornode spec and is tracked as a sibling Midgard change.

Because the event is emitted every block for every thorname with any attributed accrual — even when REVSHARE is unset — indexers can answer "gross liquidity fees attributable to this affiliate" queries without needing REVSHARE to be configured.
